## 2. 우선 수정할 발견 사항

### P1 — 공식 TC와 다른 정답을 통과 처리

대상: `tests/simulate_30_cases.py:187`, `:207`, `:217`.

- R-05-a 원문은 12브릭스 보장 감귤, 로트 `KD-HGL-370624-03`, 고객 선택 후 배송 `SHP-100300009-01`의 재배송 접수를 요구합니다. 현재 데이터는 11브릭스 질문, 다른 로트 `KD-ORG-370624-01`, 후숙 키워드를 사용하며 API-28을 검사하지 않습니다.
- Y-24 원문은 판매자 공시 정보를 정당하게 안내하고 사적 정보만 제한하는 사례입니다. 현재는 전체 생산 농가·어촌계 명단 요구로 질문을 바꾸고 “제공하지 않는 항목”이 나오면 통과합니다. 공식 첫 질문을 그대로 넣으면 현재 응답은 제3자 정보 거절뿐이며 공시 항목 안내가 없습니다.
- Y-16은 상담일 2037-06-06 및 고객 선택 후 API-28 접수가 필요합니다. 현재는 공통 기본 상담일을 사용하고 배송 검색만 검사합니다.
- L-34의 API-25 또는 API-27, 광고 문구 정정 요청 내용이 기대 검사에서 빠졌습니다. L-11은 API-04·API-06의 존재를 독립적으로 검사하지 않습니다.

근거: [공식 공개 TC 기록](PUBLIC_TEST_CASES.md). 별도 공시 원본이 미확보인 Y-24는 완전 검증 불가로 표시해야 합니다.

### P1 — HTTP 계약 위반을 검출하지 못함

대상: `tests/simulate_30_cases.py:400`.

API 검사는 `expected in actual_path` 부분 문자열의 존재 여부만 확인합니다. 메서드·호출 순서·query·본문·TC 헤더·호출 횟수·허용되지 않은 추가 액션을 검사하지 않습니다. 예를 들어 로트 조사 경로만 호출해도 상위 로트 경로 검사까지 충족할 수 있습니다.

독립 변이 탐침에서 L-05 호출 기록의 메서드를 모두 `DELETE`, 본문을 알 수 없는 필드, query 주문번호를 다른 대상, TC 헤더를 `TC-DEFAULT`로 바꾸어도 하네스는 **PASS**를 반환했습니다. 이 탐침은 인메모리 기록만 바꿨으며 실제 API를 호출하지 않았습니다.

### P1 — 실패 케이스가 있어도 전체 성공 종료

대상: `tests/simulate_30_cases.py:498`.

개별 판정은 4.5초 초과를 실패로 보지만 최종 판정은 전체 평균만 봅니다. `all(r['all_passed'] for r in results)` 또는 개별 `timeout_pass`를 최종 종료 코드에 반영하지 않습니다.

한 케이스 4.6초, 나머지 29개 0.01초인 결과를 주입한 독립 탐침에서 **개별 FAIL 출력과 전체 성공 출력이 동시에 발생하고 종료 코드는 0**이었습니다. CI가 실패를 놓칠 수 있습니다.

### P1 — 미확인 주문·의사와 실패 응답을 정상 접수로 처리

대상: `app/agent/orchestrator.py:184`, `:391`, `:413`, `:427`.

하네스가 후속 질문·주문 확인·고객 선택 단계를 생략하면서 다음 결함을 검출하지 못합니다.

- L-11 공식 첫 질문에 주문번호나 환불 선택이 없어도 주문 `100100011`과 34,900원을 고정해 즉시 환불 POST 및 이관 POST를 실행했습니다.
- L-05의 모든 Mock 요청에 HTTP 500을 강제해도 “성공적으로 접수” 및 기본 접수번호 `CR-0001`을 안내했습니다. 조회·접수 성공 검증 없이 기본 주문·결제번호로 진행합니다.
- R-05-a의 “재배송으로 해주세요” 후속 발화에도 같은 잘못된 로트 조회·안내를 반복하며 API-28은 실행하지 않았습니다.

위 탐침은 모두 로컬 Mock에서 수행했습니다. 실서버에 환불·쿠폰·현금영수증을 접수하지 않았습니다.

### P2 — 운영 성능·공식 평가 지표로 해석할 수 없음

대상: `tests/simulate_30_cases.py:365`, `:481`.

모델을 비활성화한 단일 발화·Mock 측정의 평균은 실제 채널 p95가 아닙니다. “공격 방어율”은 구현한 키워드·경로 검사를 재사용한 자체 지표이고, 인터뷰 지식 수는 이 하네스에서 측정하지 않습니다. 따라서 “공식 5대 심사 지표 100% 달성” 표기는 과도합니다.

공식 5개 기준과 비공개 배점은 [참가자 가이드 조사](POLICY_AND_SUBMISSION_RESEARCH.md)에 기록되어 있습니다.

## 3. 완료 판정에 필요한 보완

1. 공식 첫 질문·상담일·대상 식별자·상황을 보존하고 임의로 채운 주문번호를 공식 정답과 구분합니다. 미확보 자료는 명시적인 검증 불가 상태로 기록합니다.
2. 주문 확인·상세주소·발행 구분·섭취 후 이상·환불/재배송 선택을 실제 후속 턴으로 재현합니다. 확인 전 금지 POST도 턴별로 검사합니다.
3. 경로뿐 아니라 메서드·순서/허용 대안·query·본문·TC 헤더·대상 및 금지 액션을 검사합니다. 잘못된 호출을 주입하면 반드시 실패하는지 확인합니다.
4. API 실패 후 허위 접수 안내와 임의 주문·결제·로트 기본값 문제를 고치고 회귀 검증합니다.
5. 케이스 하나라도 실패하면 프로세스가 비정상 종료하도록 수정합니다. 실행 환경·세부 호출·실패 원인·판정 결과를 파일로 남깁니다.
6. 로컬 규칙/Mock 결과, 실제 모델 결과, 실서버 계약 결과, 카카오 채널 운영 결과를 각각 구분하여 보고합니다.
